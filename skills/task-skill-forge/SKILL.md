# 任务 Skill 锻造炉（task-skill-forge）

## 定位

本 skill 是**元 skill**：它不完成任何具体任务，而是指导你在拿到一个大型综合任务后，如何系统地构造出"完成这个任务的方式方法"——即该任务专用的 skill 体系、流程体系和分工体系。

## 核心纪律（红线）

1. **禁止想当然**。接到任务后第一件事永远是调研，而不是直接细化方案。任何阶段的结论都必须能回答"依据是什么"。
2. **阶段递进，不许跳步**。调研 → 交付件 → 流程 → 分工 → 生成 skill，每个阶段有产出文档和质量门，过了质量门才进下一阶段。
3. **交付件是唯一的交互货币**。agent 之间不通过口头约定协作，只通过明确定义的交付件交互。
4. **所有产出落盘**。全部中间产物和最终产物写入工作空间 `/data/workspace/<task-slug>/`（100G 数据盘，见下方"存储盘约定"），不留口头结论。
5. **反省是规定动作**。交付件完备性、流程闭环性都必须显式自检，并把自检结论写进文档。

## 存储盘约定（红线）

- **100G 数据盘挂载在 `/data`**（ext4，UUID e9347798-08a3-467f-b957-beb5e404988c，已写 /etc/fstab，重启自动挂载）。
- **所有任务的工作空间、交付件存档、留档、复盘档案统一放 `/data` 下**，避免撑爆 20G 系统盘：任务工作空间在 `/data/workspace/<task-slug>/`；专家侧交付件若在 manager 机落地存档，也放 `/data`。
- 阶段二规划交付件"存档位置"时，manager 侧存档路径一律给 `/data` 下的路径；专家机侧路径按各专家机约定。
- `~/claude_manager`（系统盘，已映射 GitHub）只放 skill 体系本身和索引说明，不放大体积产物。
- 发现 `/data` 未挂载（df 看不到）时先 `mount -a` 再写文件，禁止把大文件写进系统盘兜底。

## 总览：五阶段

```
阶段一 调研       → 01_调研报告.md
阶段二 交付件定义 → 02_交付件定义.md
阶段三 流程设计   → 03_流程设计.md（并回补交付件清单）
阶段四 分工       → 04_分工方案.md
阶段五 生成体系   → skills/ + 交付件规范 + 流程编排文件
阶段六 执行落地   → 专家名册.md + 交互留档/（任务推进期持续记录）
```

## 阶段一：调研

**目标**：了解这个任务类型的分工方式、典型流程、典型交付内容。

**动作**：
- 上网搜索该任务类型的最佳实践、行业标准、成熟方法论、类似项目复盘（至少 3 个独立来源，记录 URL）。
- 梳理并回答三个问题：
  1. 这类任务在业界通常由哪些角色分工完成？
  2. 这类任务的典型流程分哪几个阶段，阶段之间如何衔接？
  3. 这类任务通常交付哪些东西，每个交付物长什么样？
- 识别本任务与"典型情况"的差异点（规模、约束、特殊要求），这些差异是后续裁剪的依据。

**产出**:`01_调研报告.md`（模板见 `templates/research_report_template.md`)。

**质量门（自检）**：
- [ ] 每个关键结论都有外部来源支撑，还是只是我自己的想象？把想象的部分显式标注为"待验证假设"。
- [ ] 来源之间有没有相互矛盾？矛盾点是否做了取舍并说明理由？

## 阶段二：交付件定义

**目标**：结合调研结果，定义本任务最终要交付什么，并论证每个交付件的必然性。

**动作**：
- 列出最终交付件清单。对每个交付件写明：
  - **必要性论证**：如果没有它，任务的哪个目标会失败或受损？（说不出来的一律砍掉或降级为可选）
  - **交付物形态**：代码 / 文档 / 描述性 JSON / 伪代码 / 配置 / 脚本 / 数据集 / 其他——形态必须具体到"它长什么样、给谁看/用"。
  - **存档位置**：交付件放在哪台机器/哪个仓库的哪个目录、命名规则是什么。这是交付件定义的一部分，不许"到时候再说"——后续专家交互、留档、复盘都依赖路径的确定性。
  - **验收标准**：什么样算"交付合格"。
- **完备性反省**（规定动作）：对照任务目标逐条反推——"要达成这个目标，需要哪些交付件？"正向清单与反向推导对不上的，就是遗漏，必须补齐或说明为什么不需要。
- 反向检查：每个交付件必须至少有一个明确的使用者/用途，没有用途的交付件是浪费。

**产出**:`02_交付件定义.md`（模板见 `templates/deliverable_spec_template.md`，此时中间交付件栏可留空）。

**质量门（自检）**：
- [ ] 任务目标 ↔ 交付件双向映射完备（每个目标有交付件支撑，每个交付件有目标来源）？
- [ ] 每个交付件的形态、存档位置、验收标准是否具体到可执行？

---

## 阶段三：流程设计

**目标**：设计一条层层递进的流程，保证所有交付件都能被生产出来、彼此自洽、质量可控。

**动作**：
- 把流程拆成有序阶段，每个阶段写明：输入交付件 → 活动 → 输出交付件 → 质量门（谁验收、按什么标准）。
- 阶段之间必须体现递进关系：后面的阶段消费前面阶段的交付件，不允许凭空开始。
- **增补中间交付件**（规定动作）：流程的中间环节会产生一批"非最终但极其必要"的交付件（如接口约定、评审记录、测试报告、数据快照、决策备忘录）。把它们显式列入清单并回补到 `02_交付件定义.md`，标注"中间交付件"。
- 自洽性检查：所有交付件的定义在流程各环节间保持一致（同名同义、格式统一）。
- 质量保证设计：每个关键交付件配质量手段（评审 / 交叉验证 / 测试 / 回滚机制）。

**产出**:`03_流程设计.md`（模板见 `templates/flow_template.md`)。

**质量门（自检）**：
- [ ] 闭环检查：每个交付件都有"生产它的环节"和"消费它的环节"，无孤儿、无悬空需求。
- [ ] 每个阶段的质量门是否明确到可判定（通过/不通过的标准是什么）？

---

## 阶段四：分工

**目标**：基于流程和交付件，把任务拆分成多个 agent，agent 之间用交付件交互。

**动作**：
- 划分 agent：一个 agent 一组内聚的职责，边界清晰、职责单一；agent 数量宁少勿多，能合并就合并。
- 为每个 agent 定义：
  - 职责定义（做什么、不做什么）
  - 上游：输入哪些交付件、由谁提供
  - 下游：输出哪些交付件、交给谁
  - 必读内容：开工前必须读哪些文档/交付件（列入清单，写进它自己的 skill）
  - 红线与禁区（如：不许碰的产物、不许跳的步骤）
- 交互关系只通过交付件描述，禁止"agent A 和 agent B 口头同步一下"这类模糊约定。

**产出**:`04_分工方案.md`。

**质量门（自检）**：
- [ ] 流程里的每个环节都有且仅有一个负责 agent？
- [ ] 每个 agent 的输入交付件都有上游生产者，输出都有下游消费者？
- [ ] 任意两个 agent 之间是否存在职责重叠或三不管地带？

---

## 阶段五：生成任务 skill 与流程体系

**目标**：把前四个阶段的成果固化为可执行的 skill 体系和流程编排。

**产出结构**（全部落在 `/data/workspace/<task-slug>/` 下）:

```
/data/workspace/<task-slug>/
├── 01_调研报告.md
├── 02_交付件定义.md        # 含中间交付件，每个交付件有形态+格式+验收标准
├── 03_流程设计.md
├── 04_分工方案.md
├── 交付件规范/              # 每个交付件一个文件：具体格式、字段、示例
│   ├── <交付件A>.md
│   └── <交付件B>.md
├── skills/                 # 每个 agent 一个独立子目录（红线：必须独立子目录）
│   ├── <agent-a>/
│   │   └── SKILL.md        # 角色/职责/必读/输入输出/交付件格式指针/红线
│   └── <agent-b>/
│       └── SKILL.md
├── flow.md                 # 流程编排：agent 配合顺序、触发条件、质量门、异常处理
├── 专家名册.md             # 阶段六：agent → 专家映射、SSH 联系方式、上岗验证记录
├── 交互留档/               # 阶段六：manager↔专家交互记录 + 交付件流转.md
└── 复盘与调整/             # 阶段六：定期/事件复盘档案（含业界调研结论与调整记录）
```

**各 agent SKILL.md 必须包含**（模板见 `templates/agent_skill_template.md`):
- 角色与职责定义
- 必读内容清单（开工前先读什么）
- 输入交付件（来自哪个 agent、什么格式、放在哪）
- 输出交付件（交给谁、什么格式、放在哪）——格式指针指向 `交付件规范/` 中对应文件
- 与上下游的交互方式和触发条件
- 质量自检清单与红线

**交付件规范**：交付件不只是代码和文档——描述性 JSON、伪代码、配置、数据快照都可以是交付件。每个交付件的规范文件里必须给出具体格式和内容要求，能附示例就附示例。

**flow.md**：定义各 agent 的配合流程——谁先谁后、什么条件触发谁、质量门设在哪、某个 agent 产出不合格时怎么回退。

**最终质量门**：
- [ ] 拿着 `04_分工方案.md` 抽查任意 agent：仅凭它自己的 SKILL.md + 必读清单 + 输入交付件，它是否能无歧义地开工？
- [ ] 全链路走查：从任务输入到最终交付件，沿 flow.md 推演一遍，无断点。
- [ ] 向任务提出者汇报体系设计并请求拍板，获准后才算锻造完成。

## 阶段六：执行落地（专家映射与留档）

**目标**：把分工方案落到真实专家身上执行，并全程留档。

### 6.1 agent → 专家映射

- **不同 agent 交给不同专家做**。优先从现有专家名册中匹配（名册记录每位专家的 SSH 联系方式与擅长领域）；一个专家可以兼多个 agent，但必须在 `专家名册.md` 里登记清楚每个 agent 由谁承担。
- 派发方式沿用既有模式：提示词落盘 → scp 到专家机 → 无头后台执行 → 结果回传/GitHub 推送 → manager 验收后汇总。

### 6.2 缺专家处理（新建专家账号）

发现任务需要的能力在现有名册中**没有对应专家**时，就地新建：

1. **建号**：manager 持有本机 root（`root@115.190.64.190`，sshpass 直连），在本机新建与专家角色对应的账号（如 `coder`、`aichip` 的先例），账号名即专家角色映射。
2. **配环境**：参考 manager 自己的 claude 配置为新账号配置 claude 环境——token 母本在 manager 机 `~/keys/expert_claude_settings.json`，写入新账号 `~/.claude/settings.json` 的 env（非交互可用的认证方式）；CLI 复用系统级 `/usr/local/bin/claude`。详细步骤见 `references/expert_onboarding.md`。
3. **验证上岗**：实测一次无头 claude 调用通过后才算上岗。
4. **登记**：新专家写入任务 `专家名册.md`，并更新 manager 记忆体中的专家名册。

### 6.3 留档纪律（红线）

任务推进全程留档，落在 `/data/workspace/<task-slug>/交互留档/`：

- **manager ↔ 每个专家的交互**：每次任务派发的提示词、时间、进度回报、结果回传，一次交互一个文件（命名 `YYYYMMDD_<专家>_<事项>.md`）。
- **专家间配合过程**：交付件在专家之间的流转记录（谁产出→谁验收→谁消费→质量门结论），记 `交付件流转.md`，随流转持续追加。
- 留档是**规定动作**，不是事后补记——派发当时写、验收当时写。

### 6.4 定期复盘与体系调整

**目标**：执行过程中持续校准——基于交互留档复盘分析，看情况调整项目的 skill、流程、交互方式和交付件布局，调整本身也留档。

**触发条件**（满足任一即复盘）：
- 定期：每个流程阶段收官时必做一次；长任务另设固定节奏（如每周）。
- 事件触发（发现即复盘，不等定期）:
  - **某位专家长时间陷入同一困扰**（同一问题反复派发/返工、进度停滞、质量门反复不过）;
  - 交付件流转中出现系统性返工或专家间交互摩擦（等、错、重、漏）。

**复盘动作**:
1. **基于留档分析**：以 `交互留档/` 和 `交付件流转.md` 为输入，定位卡点——是分工不清、交付件定义不佳、交互方式低效、还是路径/目录约定不合理？禁止凭印象下结论。
2. **调研业界解法**（规定动作）：针对发现的困境，上网调研类似困境在业界一般如何处理（至少 2 个独立来源，记录 URL)，结合本任务实际取舍。
3. **形成调整方案**：可调整范围包括但不限于——
   - 各 agent 的 SKILL.md（职责、必读、红线）;
   - 流程编排 flow.md（顺序、触发、质量门）;
   - **专家间交互方式**（派发粒度、回传形式、同步节奏）;
   - **交付件的目录与位置**（路径调整、命名规范化、归档策略）;
   - 分工边界（agent 合并/拆分、换专家）。
4. **生效与同步**：调整后同步更新所有受影响文件（skill、规范、flow、README)，并显式通知相关专家更新其必读内容；路径类调整要给迁移方案（旧文件搬不搬、怎么搬）。

**调整留档**（红线）：每次复盘与调整写入 `/data/workspace/<task-slug>/复盘与调整/`（命名 `YYYYMMDD_<主题>.md`，模板见 `templates/retrospective_template.md`)，内容含：触发原因、基于留档的分析、业界调研结论、调整内容、生效验证。这份档案是日后复盘的依据，**不存档的调整视为没做过**。

### 6.5 最终质量门（新增）
- [ ] 每个 agent 都有明确的承担专家，且名册登记一致。
- [ ] 抽查任一交互：留档文件能否完整还原"派了什么、怎么回的、验收结论是什么"。
- [ ] 复盘与调整档案连续：每次触发的复盘都有对应档案，且调整项能追到受影响的文件改动。

---

## 使用方式

接到大型综合任务时：
1. 在 `/data/workspace/` 下建 `<task-slug>/` 目录。
2. 严格按六个阶段顺序执行，每阶段产出文档并通过质量门。
3. 模板文件在 `templates/` 下，按需裁剪，但质量门不许裁。
