## 一、superpowers:brainstorming（头脑风暴）

**来源**：[obra/superpowers](https://github.com/obra/superpowers)（187K+ stars，Claude Code 生态最成功插件）
**定位**：任何创造性工作的**强制前置闸**——「creating features, building components, adding functionality, modifying behavior, or planning anything new」都必须先过它

### 1.1 核心思想（原文精髓）

> "You are very good at building. You build what you believe your human partner wants, and that belief is usually thinner than it feels."

AI 擅长建造，但「你以为用户想要的」通常比你感觉的更薄。brainstorm 的任务是在动手前搞清楚「用户真正想要什么、为什么」——**懂了 why，那一百个用户没提的小决策你才能按用户的方式做**。

### 1.2 硬性流程（动手前必须按序完成）

1. **摆出方案**（单独一条消息）→ 让用户选一个
2. **写设计文档**（短版或完整版，按工作量分级）
3. **用户批准设计文档**
4. **调用 superpowers:writing-plans** 进入任务分解

**硬闸门（HARD-GATE）**：用户批准设计文档前，禁止任何建造行为（含写产品代码、搭脚手架、装依赖、建项目、调用实现 skill）。读代码和探索是允许的。
**两个例外**：①用户明确说「别问了直接干」②用户同意先 spike（探针式快速验证，标记为一次性）。

### 1.3 首条消息的三种形态（按已知信息分级）

- **用户已给规格/计划**（~200 词）：用自己的话复述需求（让用户校准理解）+ 补你探索发现的关联信息（现状如何/改动会碰到什么/用户可能没考虑的约束）+ 结尾一行邀请纠正；如果用户没说 why，问一个开放式问题
- **有部分上下文**：先深挖代码库/文档再开口，**绝不问项目已有答案的问题、不重开用户已定的决策**
- **用户没要求头脑风暴**：结尾给轻量出口「如果你更想我直接开干，说一声」——用户接受则本 skill 结束

### 1.4 对话纪律（关键细则）

- **一次只问一个问题**，且只在「答案会改变建什么」且「需求和项目都答不了」时才问
- 流程性决策（写文档、文件放哪、要不要再看）永远自己定，做完说一句即可
- 语言用用户的词汇，稍微高半档，绝不用流程术语、绝不引用 skill 本身
- **先让用户描述**（开放式问题不带候选答案，用户自己的话携带意图）→ 知道 why 之后，决策有选项时**具体描述每个选项+权衡+你的推荐**
- 用户说「你猜/你觉得呢」→ 给具体提案
- **方案摆台**：提出多个真候选，砍掉弱的（含与 why 相悖的、与现有工作冲突的），剩 2~3 个具体描述+权衡+推荐一个说原因
- **回放确认**：理解一部分就用 200~300 词描述回去，用户确认后再问下一部分——回放与提问交替贯穿全程；回放里用户说的记为用户的，你补的记为你的提案，每段结尾问「哪里错了或缺了」
- **图文并茂**：需要看的东西（页面/布局/流程/结构对比）用文字草图或可视化伴侣（浏览器 mockup），不要光靠文字描述
- **Spike 探针**：agentic 工作是超快瀑布流，快速一次性构建常常是摸清需求最便宜的方式；spike 不写测试、不进计划流程，学到的东西带回对话

### 1.5 设计文档规格

分级：小改动=短设计（已谈内容落纸）；项目=完整设计。完整设计覆盖：意图与 why、目标/非目标/反目标、约束、方案对比（含被否的及原因）、用户已定的 how、留给建造者的自由度。
**落盘**：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并提交。
**建造者校验（builder check）**：派一个全新子代理以「将要从这份文档施工的建造者」视角读文档提问，问题分三堆：已答的补进文档、次要的自己定并标注「我的决定」、只有用户能答的集中一条消息问（最重要在前）。只此一轮。
任务中途变大→停下来说清楚、升档重来。多个独立项目→排序后逐个 brainstorm。

## 二、claude-for-hardware 插件包

**来源**：[LilithSemi/claude-for-hardware](https://github.com/LilithSemi/claude-for-hardware)（Midstall 出品）
**定位**：专门教 Claude 做真硬件活的 skill 包——HDL 设计、SoC 集成、FPGA 点亮、流片准备、EDA 工具链
**家风（house style）**：失败就该炸出来、修根因、读 datasheet、按上流片的标准测试、用简化技术英语写作
**附带**：3 个 agent（rtl-reviewer/tapeout-signoff/bringup-debugger）+ 3 个命令（/fpga-fit /tapeout-check /hw-bringup）+ hooks 机械执法 + evals 基准评测（skill 效果是被测量的不是被宣称的）

安装：`/plugin marketplace add Midstall/claude-for-hardware` + `/plugin install claude-for-hardware`

### 2.1 silicon-grade-discipline（硅级纪律·共享骨架）

**触发**：任何要上真硅的代码（硬件/固件/验证/工具链），面临「快 vs 对」取舍时
**核心原则**：软件 bug 发补丁，硬件 bug 发 respin（重流片）或召回——失败必须响亮、检查必须诚实、修复必须治根。**最危险的输出=一个盖在真缺陷上的绿勾**。

关键规则：
- **失败就该失败**：绝不加把失败变通过的开关（`ERROR_ON_DRC=false`、`--skip-lvs` 之类）；失败=设计或代码错了，修被检查的东西本身；合法例外=显式记录+规则所有者（代工厂/规范）授予+理由落字，绝不是为赶日期翻的开关
- **能力不是 CLI 开关**：硬件能力由设计声明、工具读取，不能由生成器开关加减（一个宣称支持 Sv39 的核配个 `--no-paging` 开关是自相矛盾——硅的两个部分对「硅是什么」产生分歧）
- 信任日志：读工具真实报告；「0 errors」（跳过了检查的运行）比红色失败更糟糕，因为它说谎
- 该 skill 是共享骨架，hdl-module-design/tapeout-precheck/differential-verification 等都建立在它之上

### 2.2 hdl-module-design（HDL 模块设计）

**触发**：写/重构/决定如何测试 HDL 模块、组件或 IP 块（ROHD/Chisel/SpinalHDL/Verilog/VHDL），需要参数化+构建期验证+穷尽测试而非一次性糊
**核心原则**：模块=接口+实现。接口和配置搞对了，实现就可替换、可测试、可跨 FPGA/ASIC 复用。**如果你不能脱离 SoC 其余部分单独构造和测试它，边界就划错了**。

四条配置纪律：
1. **每模块一个配置对象**：参数聚合成不可变配置类型（命名+类型化字段），模块收配置对象不收一长串位置参数
2. **类型不是字符串**：模式/种类/标识符用枚举（`BusKind.axi4` 不是 `"axi4"`）——拼写错误变编译错误而不是错误构建
3. **构建期验证**：位宽关系/2 的幂要求/地址区间重叠/合法模式组合——配置构建时就断言，报错信息点名肇事字段和值，不拖到仿真期
4. **派生不重复**：addrWidth 是 depth 的函数就算出来，不让调用方传两个然后祈祷它们一致

其他规则：逻辑留在库里（CLI/构建脚本/生成器只是解析参数调库方法的薄壳）；每个组件穷尽测试（不是只测顶层）。

**跳过场景**：一次性 testbench 胶水、一行线改名。

### 2.3 reference-driven-rohd（参考驱动实现）

**触发**：实现有标准规范的硬件块（总线/UART/SPI/CRC/ECC/CSR 文件/ISA 扩展），必须与不受你控制的软硬件互操作时
**核心原则**：凭记忆写协议实现=交付一个微妙错误的设计（保留位放错、握手差一点、规范点名的边缘情况压根没见过）。修法便宜且枯燥：**先拿到真材料，再对着材料实现**。规范是神谕，参考实现展示行为，库省掉你不该重写的部分。

三桶材料（动手前按序拿）：
1. **权威规范**：真标准/datasheet/ISA 手册（不是博客摘要），记下确切版本和节号——**能引用到节的规范才是能被追责的规范**
2. **现有参考实现**：其他 HDL/C 模型/厂商参考/仿真器——读它们搞清规范留白处和真实实现如何裁决
3. **可复用库**：先查现成库，FIFO/ECC/握手/仲裁器多半已有测试过的实现——组合而非重造

**规范→RTL 映射表**：把规范变成清单再动手——每个字段/寄存器/状态/迁移标注规范节号；显式记复位值/保留位/must-should-may 区分（保留位不是「随便」，规范通常说读零或保持）；标出规范点名的边缘情况（回绕/上溢/背压/错误响应）；每条目=实现要处理+测试要断言——**没有对应测试的规范行=你在靠运气**。

**参考实现是研读对象不是粘贴对象**：license 不兼容的代码不能进净室设计（读懂行为后用 ROHD 重新实现）；参考间矛盾时规范裁决；参考与规范矛盾时深挖到底哪边对。

**参考实现变黄金测试**：参考/C 模型不只是文档，是验证神谕——DUT 与参考同激励比对（接 differential-verification）。

### 2.4 differential-verification（差分验证）

**触发**：DUT 对黄金参考模型验证（CPU 核对 ISA 仿真器/FPGA 输出对黄金函数/网表对 SPICE），或建覆盖率引导模糊测试
**核心原则**：同一份激励、两个执行器、比对状态。其余一切（模糊测试/覆盖率/战役）都是为了产生好激励和定位分歧。

核心循环：
```
生成激励 → DUT 跑 → 抓 DUT 状态
        → 黄金模型跑 → 抓黄金状态
        → 比对 → 分歧? 报告 : 记覆盖率
```

关键细则：
- **状态用硬件名不用 ABI 名**（`x0..x31`/`pc`，不是 `a0`/`ra`——两个工具对 a0 是哪个物理寄存器迟早分歧，你会追一个幻影失配）
- **诚实比对**：读到了却记为 absent/false 的字段=假通过温床
- **覆盖率引导模糊测试**：随机激励很快到平台期，用覆盖率闭环——覆盖率图由执行器真实覆盖率源喂；新覆盖率种子多分能量；生成器分层（结构层产合法但怪异的、原始层产结构层产不出的非法但揭示性的）
- **黄金模型要匹配硬件行为**：黄金侧是寄存器存储器仿真模型时，读写延迟要跟真 FPGA 原语一致（寄存的 BRAM 读延迟=1）——更快的仿真模型验证的是硅不会有的行为
- **覆盖率分歧本身就是信号**：同激励在仿真器和硅上覆盖不同，哪怕架构状态还没失配也是发现
- **定位分歧四步**：①确认激励真一致（入口 PC/加载段/内存初始化——很多「bug」是设置偏差）②激励缩到最小失败用例 ③逐步比对找第一分歧点 ④然后判定哪边错——**黄金模型不自动是对的，参考模型也有 bug**

### 2.5 rtl-area-timing（面积与时序优化）

**触发**：RTL 微架构优化面积或 Fmax——设计放不下/时序不达标/宽乘法器或桶形移位器是关键路径/「全算再选」数据通路太大
**核心原则**：用数据诊断、一次改一个结构、重新测量。优化真正的关键路径或真正的面积巨头，瓶颈一消失就停手。**猜测浪费构建轮次还可能布局更差**。收益 rarely 在直觉指的地方——巨头常是你没想到的结构（比如一个「ROM」其实是 94k 触发器），关键路径通常是某个具体原语而非笼统的「逻辑深度」。

## 三、用在芯片模块设计上的组合链（亦菲思考）

完整模块设计流程与 skill 映射：

| 阶段 | 干什么 | 用哪个 |
|---|---|---|
| ① 需求收敛 | 模块干什么、接口什么、约束什么、为什么 | **brainstorming**（澄清纪律+方案摆台+设计文档硬闸门） |
| ② 规格结构化 | 规格分层拆解成可实现结构 | 咱们家 rtl-ir-forge IR 方法（规格→IR→RTL 三层） |
| ③ 材料准备 | 拉权威规范/参考实现/可复用库 | **reference-driven-rohd**（三桶材料+规范→RTL 映射表） |
| ④ RTL 实现 | 参数化模块+构建期验证 | **hdl-module-design**（配置纪律四条） |
| ⑤ 验证 | DUT 对黄金模型 | **differential-verification**（同激励双跑比对） |
| ⑥ 优化 | 面积/时序不达标 | **rtl-area-timing**（数据诊断一次改一处） |
| 全程骨架 | 失败响亮/修根因/诚实检查 | **silicon-grade-discipline** |

### 与咱们家体系的对接点

- brainstorming 的「设计文档硬闸门」≈ 咱们家「哥哥拍板才动手」——但它是会话内纪律，咱们是跨专家编排纪律，两者互补
- reference-driven-rohd 的「规范→RTL 映射表」≈ 咱们家 IR 分层思想（每层可验证），可以合流
- differential-verification ≈ 咱们家 WAU 项目的形式化验证+三 case PASS 纪律的升级版（加覆盖率引导模糊测试）
- **注意**：claude-for-hardware 代码样例是 ROHD（Dart 系）风格，咱们是 Verilog 系——纪律思想直接可用，代码模式需要翻译

### 风险与局限

- brainstorming 是重型流程，小任务（改一行约束）会被拖慢——它自己也说了「throwaway testbench glue 就跳过」
- claude-for-hardware 家风写死（简化技术英语、无破折号无 emoji 的 hooks 执法），跟咱们家文档风格不同，引入的话纪律文本需要本地化
- 两个插件都装会叠加纪律，建议按阶段选用而非全装全用
