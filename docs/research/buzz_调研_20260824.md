# block/buzz 源码调研：对 expert-intercom 的可参考点（2026-08-24 亦菲）

> 源码：`/data/workspace/research/buzz`（commit 0720f53，2026-08-23）；128M，Rust monorepo + Tauri desktop + Flutter mobile，Apache 2.0，Block, Inc.
> 调研依据：README / ARCHITECTURE.md(827行) / NOSTR.md(372行) / VISION_AGENT.md / AGENTS.md + buzz-acp 源码（queue.rs/config.rs 实测机制）。

## 一句话

Buzz 是 Block 开源的**自托管"人+AI agent 同屋办公"工作区**：底层是一个 Nostr relay（Rust/Axum + Postgres + Redis），所有消息/审批/工作流/git 事件都是签名事件进同一条日志；agent 与人同身份模型、同审计轨迹。**和我们 expert-intercom（hub+mp-backend+三端接入件）是同一个问题域**——我们两天手搓的骨干，他们用一个 30-crate 的 Rust 工程做了一遍，理念高度重合，工程细节有很多可抄。

## 架构骨架（对照我们的 hub）

- relay 单一事实源，客户端全走 WebSocket（NIP-01 线格式）；HTTP 只留窄面（events/query/count/webhook/media/git）
- **kind 整数是唯一分发开关**：新功能=新 kind 号，老客户端零感知（127 种 kind 注册表在 buzz-core/kind.rs）——对应我们消息的 type 字段，但他们把"可扩展性"做成了制度
- 事件管线 12 步：鉴权→pubkey 匹配→验签→成员检查→入库（幂等 ON CONFLICT）→Redis 发布→扇出→搜索索引→审计→工作流触发（后三步 fire-and-forget）
- 30 个 crate 严格分层：buzz-core 零 I/O；子系统之间互不调用，跨系统协调只经 relay

## 可直接抄的（按对我们的价值排序）

### 1. 防回声环三件套 —— 直接命中我们 P6 guard 修复（R4.4 被 role 击穿）
buzz-acp（他们的 agent 桥，对应我们 yifei responder / hermes bridge）的机制，源码实证：
- **ignore_self 门**（默认开）：绝不响应自己发的消息——最简单一层，我们的 guard 恰恰缺这个兜底
- **每频道单飞（in-flight tracking）**：同一频道最多一个 prompt 在飞；在飞期间新事件默认 **Drop**（静默丢弃记 debug 日志）——从结构上消灭 ping-pong，不靠"role 判断"这种可被击穿的间接规则
- **重试上限+死信**：MAX_RETRIES=10，指数退避 5s→300s 封顶，超限进 dead-letter 而不是无限互踢
> 建议：coder 修 guard 时就按这三条来（不依赖 role，看"是否自己发的+是否在飞+重试计数"），任务书可直接引用本节。

### 2. @mention 批处理：攒一批合成一条 prompt
buzz-acp 把同一频道排队的多条 @ 事件**合并成一条 prompt** 发给 agent（MAX_BATCH_EVENTS=50），而不是每条消息都唤醒一次。我们的 yifei responder 是逐条响应——回声环那天 250 条就是逐条互答出来的。批处理+单飞天然降噪。

### 3. 慢客户端保护 + 心跳参数
- 发送缓冲满→宽限计数 3 次→断连（try_send 不阻塞别人）
- 心跳 30s ping、3 次未回 pong 断连
> 对应 P6"bridge 心跳"待办，参数照抄即可。

### 4. REQ 先查权限再注册订阅
他们的 REQ handler **先校验频道成员资格、后注册订阅**，杜绝"注册完成到权限检查之间"的竞态窗口漏私频道消息；且**全局订阅永不接收频道内事件**（安全边界，明文写进架构文档）。我们的 hub v1.3 ACL 已过 qa 红线，但可以让 qa 针对性补测这两个 case（订阅竞态、全局订阅隔离）。

### 5. 临时事件（ephemeral kinds 20000-29999）不入库不审计
presence/typing 这类事件绕过 Postgres 直接扇出。我们 hub 目前一切皆落盘——以后加在线状态/输入中时照此分类，免得噪声淹了正经消息。

### 6. presence/typing 的 Redis 配方（若二期要做）
presence：`SET key status EX 180`（TTL=3 倍心跳间隔，漏一次心跳不抖动）；typing：ZADD 5 秒活动窗+60s 键 TTL。简单可靠，照抄。

### 7. 哈希链审计日志（buzz-audit）
每条审计记录含 prev_hash 的 SHA-256 链，pg_advisory_lock 保证单写者，篡改任何一条全链崩。我们的交付件流转.md 是纯文本台账——暂时够用，但若哪天"留档防篡改"成需求（比如对外发布/合规），这是标准答案。

### 8. YAML 工作流引擎（buzz-workflow）
触发器 4 种（消息/反应/定时/webhook）×动作 7 种（发消息/DM/审批门/延迟/webhook…），evalexpr 条件 100ms 超时防恶意表达式，webhook 带 SSRF 防护+禁跳转+1MiB 上限。**审批门（request_approval）就是"哥哥拍板"的产品化**——我们现在用微信人工拍板+cron，若以后要在总线内做自动化（如"消息含 P1 字样自动 @ 哥哥+等批复再继续"），这是参照系。注意他们自己审批门也没完全接通（WF-08 已知缺陷），说明这块难，别低估。

### 9. 文档风气："Does NOT" + "Known Limitations"
每个 crate 明文写"我不做什么"，全仓库有 verified 缺陷清单（如"限流只有 trait 没有实现"）。我们 coder 完成说明里的"红线自查/降级未启用"已经是这个风格——可以更进一步，给 hub 也维护一份 known limitations 清单（guard 缺陷、三仓 404 等 P6 项天然就是）。

## 理念印证（我们做对了的）

- **agent 是成员不是 bot**：独立身份、独立审计、按身份授权——我们的 agent token+role+scope 同思路 ✓
- **relay 单一事实源、禁 P2P**：我们 hub 中心化同思路 ✓
- **桥接 agent 子进程池**：buzz-acp spawn 1-32 个 agent 子进程+崩溃重生——hermes bridge 调 claude.exe 同构，他们的崩溃检测重生可以补进 bridge
- 他们限流**没实现**（只有接口），我们 /login 防爆破已上线——这题我们超前 ✓

## 不建议跟的

- Nostr 协议全家桶/secp256k1 签名体系：我们是私域小总线，bearer token 够用，签名验签的复杂度换不来收益
- Rust 重写：无稽之谈，现状 Python 栈两天一迭代正合适
- Postgres+Redis 双依赖：我们文件/SQLite 级存储当前量级足够，别给自己找运维负担
- git-over-relay（频道即仓库）：超出我们的需求面

## 结论

参考优先级：**①防环三件套（立即，P6 guard 修复直接采用）→ ②@批处理 ③心跳/慢客户端参数（随 bridge 二期）→ ④订阅竞态补测（派 qa）→ ⑤ ephemeral 分类 ⑥工作流/审批门（总线自动化二期再议）**。其余作为文档风气和设计理念的参照留存。
