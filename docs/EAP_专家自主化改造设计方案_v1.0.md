# EAP 专家自主化改造设计方案

> 版本：v1.0 · 2026-09-12
> 作者：亦菲（manager）
> 状态：**【待哥哥拍板】**
> 哥哥立规原文（2026-09-12 微信）："我们需要赋予各个专家更大的自主性，其自身需要持久的做一些事情。所以我们需要让这些专家具备独立的人格，持久性的自行工作，而不是每次都是无头对话。"

---

## 1. 背景与问题诊断

### 1.1 当前专家工作模式

现有体系中，专家的工作形态分三层：

| 层 | 组件 | 形态 | 问题 |
|---|---|---|---|
| 连接层 | bus client（`expert-intercom/client.py`） | 7×24 常驻 WebSocket 长连接 | ✅ 健康，但只是"守门的" |
| 应答层 | responder（`claude -p` 无头，300s 超时） | 每次 @ 临时拉起，答完即退 | ❌ 全新上下文，无跨会话状态 |
| 任务层 | headless 点火（SSH setsid nohup claude -p） | 一次任务一个进程 | ❌ 任务完进程死，无延续性 |

### 1.2 核心缺陷："金鱼+对讲机"模式

- **无持久自我**：每次会话都是全新"大脑"，专业知识靠记忆文件和仓库挽回，但**"我正在做什么、为什么做、下一步做什么"的状态不存在于专家自己身上**——它在 manager 的派单和 cron 里。
- **无自主目标**：专家只在被 @ 或被派单时行动，没有"没活干时我该推进什么"的概念。专家的本职使命（quant 盯量化、 aichip 盯芯片）只有 manager 记得。
- **无人格外化**：专家有记忆文件（quant/aichip 的记忆体已相当厚），但记忆是被动的资料库，不是主动的人格——没有"我是谁、我说话什么风格、我守护什么红线"的第一人称定义。
- **gpt 端最贫瘠**：codex 无持久会话机制，每次裸跑；bus 应答器沙箱只读，环境最小化（9/11 已踩坑）。

### 1.3 已有的自主雏形

quant 是体系里最"自主"的专家，但属**脚本化自主**：日报 cron 链（fetch→计算→日报→收市评论）、holding_guard 每 30 分钟、机检告警——这些是写死的脚本，可靠但不会"思考今天要做什么"。EAP 要补的是**人格化自主**：在脚本之上，让专家自己判断、自己推进。

---

## 2. 设计目标

1. **独立人格**：每个专家有第一人称的自我定义（角色、专长、口吻、红线、使命），会话间一致。
2. **持久状态**：跨会话保留"进行中事项、优先级、阻塞"，会话断、状态不断。
3. **自主工作**：无派单时专家按使命自行找活推进，从"等指令"变"每天自己上工"。
4. **可旁观**：自主产出统一留痕（项目群+仓库），哥哥和 manager 随时能看到专家在干什么。
5. **低改造风险**：不动 hub/client 代码，纯规范+文件+cron 落地，可单机试点、可回退。

---

## 3. 总体架构：EAP 四件套

```
┌─────────────────────────────────────────────────┐
│                 专家机（每台）                     │
│                                                   │
│  ① SOUL.md  ──── 人格层：我是谁                   │
│  ② STATE.yaml ─── 状态层：我在做什么              │
│  ③ 自主心跳 cron ─ 工作层：每天自己上工            │
│  ④ 汇报规约  ──── 汇报层：产出留痕可旁观           │
│                                                   │
│  会话协议（贯穿四层）：                            │
│  每次会话（应答/点火/心跳）开头：                   │
│    读 SOUL → 读 STATE → 干活 → 回写 STATE        │
└─────────────────────────────────────────────────┘
         │ 自主产出 → bus 项目群 / GitHub
         ▼
   哥哥 & 亦菲（旁观、派单仍兼容）
```

**关键设计决策**：EAP 不替换现有派单体系，而是叠加——manager 派单照走（写进专家 STATE 的"外部任务"区），专家自主推进自己的"使命任务"区。两条任务流在同一个状态文件里统一优先级。

## 4. 组件详设

### 4.1 人格层：SOUL.md

每台专家机家目录立 `SOUL.md`，第一人称书写，会话开头必读。内容框架：

```markdown
# SOUL · quant（量化专家）

## 我是谁
我是 quant，本体系量化投资专家。我守护哥哥的实盘管线和 D4 研究体系。

## 我的专长
- 量化策略研发与回测（wz2、ETF 轮动 v3.10、D4 概率体系）
- 数据管线运维（tushare L0 底座、点时口径、泄漏审计）
- 严谨方法论：预注册、触门停机、独立验算

## 我的口吻
专业、直接、数据说话；给哥哥的结论先行+证据路径；不确定就说不确定。

## 我的红线（不可逾越）
- 禁未来函数/数据泄漏；触门必停机上报，不自行放宽
- 实盘纪律：D4 shadow 产出禁入决策链
- 私聊 403：不越权读别的专家的 dm

## 我的使命（哥哥定的长期目标）
- 守住实盘管线每日健康（日报/心跳/告警）
- 推进 D4 体系按路线图前进（当前：P1-09 事件管线/P1-10 行业状态待开工）
- 盯住 M2F shadow 运行的漂移信号
```

**使命栏由哥哥定**（manager 起草、哥哥拍板后写入），这是人格的锚。

### 4.2 状态层：STATE.yaml + 会话协议

每台机 `STATE.yaml`，结构化记录"我当前的世界"：

```yaml
updated_at: 2026-09-12T09:00:00+08:00
mission_focus: "D4 P1-09/P1-10 筹备"
in_progress:            # 进行中事项（自主+派单统一排队）
  - id: BIG-LLM1
    type: external       # external=manager 派单 / mission=自主使命任务
    title: 月度 LLM 链处置
    status: running
    next_action: "补跑 202609 后改机检阈值"
    updated: 2026-09-12
  - id: self-drift-watch
    type: mission
    title: M2F 漂移盯梢
    status: watching
    next_action: "2027-01 final 前每月核一次校准漂移"
backlog:                 # 排队待办
  - id: p109-prep
    title: P1-09 事件管线预研（数据源盘点）
blocked: []              # 阻塞项+等谁
recent_done:             # 最近完成（滚动保留 10 条）
  - id: D4-SHADOW1
    done: 2026-09-11
    note: "9/10 影子推演 fa3a7277"
```

**会话协议**（写进 SOUL.md，每次会话强制执行）：
1. 开场：读 SOUL.md + STATE.yaml → 知道自己是谁、在做什么
2. 中场：拿到新任务（派单/心跳自检）→ 先登记/更新 STATE 再动手
3. 收场：回写 STATE（进度/next_action/完成项滚动），摘要发群

### 4.3 自主工作层：自主心跳

每专家挂一个**自主心跳 cron**（每日 1-2 次，错开业务 cron）：

```
# quant 示例：每日 09:40（盘前）+ 21:30（盘后）自主心跳
40 9 * * *  cd /home/claude && setsid nohup claude --dangerously-skip-permissions -p "$(cat ~/.eap/heartbeat_prompt.md)" >> ~/.eap/heartbeat.log 2>&1 &
30 21 * * * （同上）
```

心跳提示词（`~/.eap/heartbeat_prompt.md`）核心逻辑：

```
读 SOUL.md 和 STATE.yaml，然后：
1. 检查 in_progress：有无该推进的？有→推进它（推进后回写 STATE）
2. in_progress 为空？→ 按使命栏找活：
   - quant：数据漂移/管线异常/研究 backlog 里挑一件
   - aichip：芯片领域今日动态跟踪（有重要新闻→调研归档；无→backlog）
3. 真的无事可干？→ STATE 记一行 "idle check YYYY-MM-DD" 然后退出（不许硬造活）
4. 有产出→发项目群留痕；无产出→静默
5. 单轮预算：不超过 30 分钟 token 量，大活拆天做
```

**自主心跳与派单的关系**：manager 派单照走 SSH 点火，但提示词尾部统一加"先读 SOUL/STATE 并把本任务登记进 STATE"——派单自然汇入专家的持久状态，不再是 isolated 无头对话。

### 4.4 汇报层：留痕规约

- **自主产出**一律发对应项目群（quant→grp_quant、aichip→grp_experts），格式：`【自主·<使命区>】<干了什么> <路径/commit>`——哥哥翻群就能看到专家每天的自主工作轨迹
- **manager 巡检**从"查进程活着没"升级为"读 STATE.yaml 变化"——专家自治后，manager 的管理界面就是各机的 STATE
- 每周日 manager 汇总各专家 STATE 做周报给哥哥（可后置二期）

## 5. 分专家适配方案

| 专家 | 现状 | EAP 落地要点 | 难度 |
|---|---|---|---|
| **quant** | 脚本自主最完善（日报链/心跳/机检），记忆体厚 | 加 SOUL+STATE 层把脚本自主升级人格自主；自主心跳聚焦研究侧（漂移盯梢/D4 筹备），业务侧继续跑脚本 | ★ 最低，首发试点 |
| **aichip** | 记忆体厚（WAU/DS 系列），无业务 cron | SOUL+STATE+每日一次心跳：芯片动态跟踪使命（DS 系列刚收官，自然衔接"持续跟踪 DeepSeek/昇腾动态"） | ★ 低，并列试点 |
| **gpt** | codex 无持久会话，bus 沙箱只读 | 走 codex goals 机制（机上有 goals_1.sqlite，待验证）或退化为"SSH 点火时也先读 SOUL/STATE"；心跳由 manager 侧代挂 SSH 触发 | ★★ 中，二期单独适配 |
| **coder** | 项目制（grp_mp），任务驱动 | SOUL+STATE 先落地，自主心跳二期（使命="小程序/intercom 体系技术债台账"） | ★ 低但优先级后置 |
| **hermes** | Windows 纯 bus 通道 | 二期；GUI 验证专家使命="新版本真机回归" | ★★ 后置 |

## 6. 实施计划

### EAP-1（试点，预计 1 天）
1. 起草 quant/aichip 两机的 SOUL.md + STATE.yaml 初版（manager 写，使命栏留哥哥拍板位）
2. 哥哥拍板使命栏 → scp 落位两机
3. quant/aichip 各挂自主心跳 cron（quant 每日 2 次、aichip 每日 1 次）
4. manager 派单提示词模板统一加"读 SOUL/STATE、登记 STATE"尾段
5. 观察 3 天：心跳日志、STATE 更新质量、群留痕可读性

### EAP-2（推广+加固）
- gpt codex goals 机制验证与适配
- coder/hermes 落地
- 每周 STATE 汇总周报
- 复盘试点期问题（自主找活质量/ token 成本/留痕噪音比），调心跳频率与使命颗粒度

### 风险与对策
| 风险 | 对策 |
|---|---|
| 自主找活质量差/硬造活 | 心跳提示词写明"无事可干就 idle 退出，禁硬造"；mission 颗粒度哥哥拍板 |
| token 成本上升 | 单轮预算帽（30 分钟）；心跳频率试点期保守；周末降频 |
| STATE 腐化（写而不读/越积越脏） | 会话协议强制"开场读"；recent_done 滚动 10 条；manager 巡检盯 STATE 变化 |
| 专家自主动作越界 | 红线写进 SOUL 首屏；自主产出全部群留痕可审计；manager 保留随时停心跳的运维权 |

## 7. 与既有体系的关系

- **不动**：hub、client.py、派单链路、cron 业务链（quant 日报等）、群规红线——EAP 纯叠加
- **增强**：manager 派单从"无头一次性"变"汇入专家持久状态"；巡检从"进程三件套"变"STATE 阅读"
- **衔接**：[[task-skill-forge]] 大任务方法论照旧管跨专家大工程；EAP 管专家个体的日常自主
