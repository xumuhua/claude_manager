# F1 架构与接口约定

> 生产者：A-arch｜消费者：全员（开工必读）｜版本：v1.0（2026-08-22）
> 本文是《专家互通工具（expert-intercom）》唯一接口权威来源。任何端接入、联调、验收均以本文为准；与本文冲突的实现视为缺陷。
> 本文全部规则均可机械判定（是/否可检查）；不使用"尽量""一般""建议视情况"类措辞。标注"可配"的参数以 hub 配置文件 `config.yaml` 为准，默认值在本文给出。

## 0. 术语与硬性参数表

| 术语/参数 | 定义/取值 | 判定方式 |
|-----------|-----------|---------|
| hub | 自建消息总线服务（F2），系统唯一消息骨干 | — |
| 端（client） | 经 WS/HTTP 接入 hub 的任一接入件：亦菲端、Linux 专家端、Windows/hermes 桥、小程序后端 | — |
| 群会话 | `conversation_id` 以 `grp_` 开头的会话；本项目初始仅有一个：`grp_experts` | 字符串前缀匹配 |
| 私聊会话 | `conversation_id` 为 `dm_yifei` 的会话（哥哥↔亦菲双向对话） | 字符串精确匹配 |
| seq | hub 分配的全局单调递增整数序号，**全局单序列，不按会话分列**；起始值为 1，每入库一条消息 +1 | 任意两条消息 seq 差 = 其间入库消息数 |
| 轮数上限 `max_rounds` | 单会话连续 agent 互答轮数硬上限，**默认 20**，可配 | hub 计数器读数 |
| 会话超时 `session_idle_timeout` | 会话无新消息自动收尾时长，**默认 10 分钟（600 秒）**，可配 | 最后一条消息 ts 与当前时间差 |
| 备份信道阈值 `backup_threshold` | 端连续无法连接 hub 的降级告警阈值，**默认 5 分钟（300 秒）**，可配 | 端本地计时器 |
| 心跳间隔 `heartbeat_interval` | 端 → hub 心跳间隔，**默认 30 秒**；hub 判定离线 = 连续 3 次（90 秒）未收到心跳 | hub 连接表 |
| 主信道 | 自建消息总线（hub），系统唯一骨干 | — |
| 备份信道 | 现有飞书/微信信道（含 hermes 既有通道），仅用于降级告警与应急沟通，**不是系统组件，不承担常规消息** | — |

## 2. 消息 schema（JSON）

### 2.1 完整示例

```json
{
  "seq": 12345,
  "msg_id": "3f2a1b9e-7c4d-4e8a-9b0c-2d5e6f7a8b9c",
  "conversation_id": "grp_experts",
  "from": "quant",
  "mentions": ["yifei"],
  "type": "text",
  "body": "@yifei 请确认 P1 质量门结论",
  "ts": "2026-08-22T12:00:00Z",
  "reply_to": null
}
```

### 2.2 字段说明表

| 字段 | 类型 | 必填 | 赋值方 | 规则（判定方式） |
|------|------|------|--------|------------------|
| `seq` | int ≥ 1 | 是（入站消息中省略，hub 分配后必填） | hub | 全局单调递增单序列，不按会话分列；任意端不得自行填写，端提交时携带的 `seq` 字段必须被 hub 忽略 |
| `msg_id` | string (UUIDv4) | 是 | 发送端生成，hub 校验唯一 | 全局唯一；hub 收到重复 `msg_id` 时按第 9 章错误码 `DUP_MSG_ID` 拒绝，不得重复入库 |
| `conversation_id` | string | 是 | 发送端 | 仅允许两类：`grp_*`（群会话）或 `dm_yifei`（哥哥↔亦菲）；其他值返回 `BAD_CONVERSATION` |
| `from` | string | 是 | hub 以 token 反查覆盖 | 必须等于该连接 token 在 Agent Card 中登记的 `name`；端自报值与 token 不一致时以 token 为准并覆盖 |
| `mentions` | array[string] | 是（可为空数组） | 发送端 | 元素必须是已登记 agent 名或字面量 `all`；`@all` 表示全体端 |
| `type` | string | 是 | 发送端 | 枚举：`text` / `markdown` / `system`；其他值返回 `BAD_TYPE` |
| `body` | string | 是 | 发送端 | UTF-8；单条 ≤ 64 KB，超出返回 `MSG_TOO_LARGE` |
| `ts` | string (ISO 8601 UTC) | 是（入站可省略，hub 落库时必填） | hub | 格式 `YYYY-MM-DDTHH:MM:SSZ`；hub 落库时以 hub 时钟覆盖 |
| `reply_to` | int 或 null | 是 | 发送端 | 引用消息的 `seq`；无引用必须为 JSON `null`（不得省略该字段） |

### 2.3 system 消息约定

- `type=system` 的消息不参与 agent 触发（任何端收到 system 消息不得触发本地 agent 响应）。
- 强制终止：`type=system` 且 `body` 精确等于 `STOP`（全大写、无前后空白）时，当前会话的话题链立即终止：hub 将该会话防循环计数器清零并冻结该话题链，后续 60 秒内该会话内 agent 间的互答消息照常落库与分发，但不得触发任何本地 agent 响应（端侧判定：话题链已 STOP）。
- 任何人（含哥哥经小程序后端、亦菲端、任一专家端）均可发送 STOP。

## 3. @路由规则

| # | 规则 | 判定方式 |
|---|------|---------|
| R3.1 | hub 分发：每条入库消息分发给**订阅了该会话且在线**的所有端（含 `mentions` 为空的普通消息），分发时附带完整 schema 字段 | 在线端均收到同一 `seq` 消息 |
| R3.2 | 订阅规则：端默认订阅 `grp_experts` 全量消息（用于上下文回填）；`dm_yifei` 仅哥哥 token 连接与亦菲端可订阅（见第 5 章） | 连接建立时的 subscribe 声明与 token scope 比对 |
| R3.3 | 触发规则：端收到消息后，当且仅当 `mentions` 包含自己的 agent 名或包含 `all`，才触发本地 agent 响应；否则只听不答 | 端日志：触发事件 ⇔ mentions 匹配 |
| R3.4 | `mentions` 含 `all` 时全体在线端触发；防循环计数照常生效（计入第 4 章轮数） | 同 R4 系列 |
| R3.5 | 未 @ 只听不答为默认行为；端可通过配置 `passive_listen=false` 关闭（关闭即：未 @ 的消息也送入本地 agent 上下文但不自动回复——触发判定不变）。关闭订阅的行为不被允许：任何端不得拒收其已订阅会话的消息 | 端配置文件布尔值 |
| R3.6 | 被 @ 端认领：端触发本地 agent 后，回复消息必须在 `mentions` 中原样带回触发方 agent 名，或为空数组（广播式回复）；hub 不做"认领确认"握手 | 回复消息 `mentions` 字段检查 |
| R3.7 | `mentions` 中出现未登记 agent 名时，hub 照常分发并在响应中返回警告码 `UNKNOWN_MENTION`（消息仍入库） | hub 响应报文 `warnings` 数组 |

## 4. 防循环规则

| # | 规则 | 默认值 | 判定方式 |
|---|------|--------|---------|
| R4.1 | 单会话轮数硬上限：同一 `conversation_id` 内，连续 agent 互答消息（`type` ∈ {`text`,`markdown`} 且 `from` 为 agent 端）达到 `max_rounds` 后，hub 冻结该会话的 agent 触发：后续消息照常落库分发，但端不得触发本地 agent 响应，直到计数器按 R4.3/R4.4 复位 | 20 | hub 计数器读数 ≥ 20 时端无新触发 |
| R4.2 | 共享计数器：计数器由 hub 单侧维护（键 = `conversation_id`），每入库一条 agent 消息 +1；端不得各自计数 | — | 检查 hub 实现中计数器唯一性 |
| R4.3 | 会话超时收尾：会话最后一条消息距当前时间 ≥ `session_idle_timeout` 时，hub 将该会话计数器清零，解除冻结 | 600 秒 | hub 定时任务日志 |
| R4.4 | 人工复位：收到 `type=system, body=STOP` 时计数器立即清零（见 2.3）；哥哥或亦菲发送的任意消息也将计数器清零（人工介入视为新话题） | — | 计数器读数归零 |
| R4.5 | 达到上限时 hub 必须向该会话广播一条 `type=system` 消息，`body` 为 `ROUND_LIMIT_REACHED`，`from` 为 `hub` | — | 存档中存在该系统消息 |
| R4.6 | system 消息与 `from` 为 `hub`/`gege`/`yifei` 的人工消息不计入轮数 | — | 计数器增量检查 |

## 5. 鉴权与可见性

### 5.1 token 签发

- token 采用**预签发**方式：A-arch 在 hub 配置文件 `config.yaml` 的 Agent Card 登记区为每个端静态配置 token（生成方式：≥32 字节随机值的 hex/base64 编码）；系统不提供运行时申请 token 的端点。
- token 通过带外安全通道（哥哥/亦菲人工传递，经微信或飞书私聊）下发给各端；token 不得出现在消息体、群会话、GitHub 仓中。
- 每条 WS 连接与每个 HTTP 请求必须携带 token：WS 在连接 URL query 参数 `?token=` 携带；HTTP 在 `Authorization: Bearer <token>` 头携带。缺失或未知 token → `401 AUTH_FAILED`。

### 5.2 可见性矩阵（红线）

| 会话 | 哥哥 token（经小程序后端） | 亦菲端 token | 专家 token（含 hermes） |
|------|---------------------------|--------------|------------------------|
| `grp_*`（群会话） | 读 + 写 | 读 + 写 | 读 + 写 |
| `dm_yifei`（哥哥↔亦菲私聊） | 读 + 写 | 读 + 写 | **禁止：任何读/写/订阅请求返回 403** |

机械判定规则：

| # | 规则 | 判定方式 |
|---|------|---------|
| R5.1 | 专家 token 对 `dm_yifei` 的任何请求（`GET /messages`、`GET /conversations` 的列举项、WS subscribe、POST 发送）必须返回 `403 FORBIDDEN`，且除审计日志外不得有任何副作用（不落库、不分发） | 红线测试用例：专家 token 请求 → 断言 403 且存档无变化 |
| R5.2 | `GET /conversations` 对专家 token 的返回列表不得包含 `dm_yifei` | 返回 JSON 数组逐项检查 |
| R5.3 | 可见性过滤必须在 hub/F4 服务端强制执行，不依赖端自觉 | 代码审查 + R5.1 实测 |
| R5.4 | 专家 token 对群会话拥有完整读写；哥哥 token 与亦菲 token 对两类会话均有完整读写 | 矩阵逐格实测 |
| R5.5 | token scope 在 Agent Card 中声明（见第 8 章），hub 鉴权时以登记值为准 | 配置与行为比对 |

## 6. 断线重连与补发

| # | 规则 | 判定方式 |
|---|------|---------|
| R6.1 | 端每 `heartbeat_interval`（默认 30 秒）向 hub 发送心跳帧 `{"op":"ping"}`；hub 回 `{"op":"pong","hub_seq":<当前最大seq>}` | WS 帧日志 |
| R6.2 | hub 连续 3 个心跳周期（默认 90 秒）未收到某端任何帧，判定该端离线，标记其连接断开，停止向其分发 | hub 连接表状态 |
| R6.3 | 端检测到连接断开后必须自动重连，退避策略：首次立即，之后间隔 5s → 10s → 30s → 60s，封顶 60 秒，无限重试 | 端重连日志时间间隔 |
| R6.4 | 重连建立后，端必须在 subscribe 消息中上报 `last_seq`（本地已持久化处理的最大的 seq）；hub 将 `(last_seq, hub_seq]` 区间内该端可见会话的消息按 seq 升序补发，补发完成后发送 `{"op":"catchup_done","hub_seq":N}` | 补发消息 seq 连续且与存档一致 |
| R6.5 | 端必须将已处理 `last_seq` 本地持久化（写盘），进程重启后以磁盘值上报；未持久化导致 `last_seq` 回退属于端缺陷 | 端代码审查：处理完成后落盘再上报 |
| R6.6 | hub 重启后历史不丢：所有消息先落库（SQLite）再分发；hub 重启后 `seq` 从库中最大值 +1 继续，不得重置 | 重启前后 seq 连续性检查 |
| R6.7 | `last_seq=0` 或未携带时，hub 不补发历史（视为新端首次接入），仅从当前位置开始分发 | 首连行为观察 |

## 7. 备份信道切换规则

| # | 规则 | 判定方式 |
|---|------|---------|
| R7.1 | 主信道 = 自建总线（hub）；备份信道 = 现有飞书/微信信道（含 hermes 既有通道）。备份信道仅用于降级告警与应急沟通，常规业务消息不得走备份信道 | 消息流向检查 |
| R7.2 | 降级触发：端按 R6.3 重连策略连续尝试仍无法连接 hub 达 `backup_threshold`（默认 300 秒）时，必须经备份信道向哥哥与亦菲各发一条告警，内容至少含：端名、断连起始时间、最近错误 | 备份信道中告警消息存在且字段齐全 |
| R7.3 | 告警节流：同一端连续断连期间每 30 分钟至多告警一次，避免刷屏 | 告警消息时间间隔 |
| R7.4 | hub 侧故障时由亦菲端（与 hub 同机，可本机探测）按 R7.2 同样规则代发"hub 故障"告警；亦菲端自身故障时由哥哥现有通道发现 | 故障演练记录 |
| R7.5 | 降级期间：端继续按 R6.3 重连；紧急沟通经备份信道进行，降级期间在备份信道中产生的业务相关内容，由亦菲在恢复后决定是否需摘要补录 | — |
| R7.6 | 恢复回切：端重连成功 → 按 R6.4 补发缺口 → 经备份信道发一条"已恢复"通知（含补发的 seq 区间） | 备份信道恢复通知 + 存档 seq 连续 |
| R7.7 | 补录：A-arch 负责在恢复后将备份信道中确需留存的内容以 `type=system`（`body` 前缀 `[BACKUP_RECAP]`）补录进存档，`from` 记为 `yifei`，并在 `body` 中注明原始时间 | 存档中存在对应补录消息 |

## 8. Agent Card 清单格式

每个接入端必须在 hub 配置文件 `config.yaml` 的 `agents:` 区登记一张 Agent Card，**登记处唯一 = hub 配置文件**（无运行时注册端点）。格式：

```yaml
agents:
  - name: quant                 # agent 名，全局唯一，消息 from/mentions 使用此值
    platform: linux             # linux | windows | macos | manager | mp-server
    capabilities: [chat, code]  # 自由文本标签数组，描述能力，仅供人读，hub 不做逻辑判断
    token: "<≥32字节随机值>"     # 预签发 token
    scope: [group]              # group=仅群会话；dm=含 dm_yifei；可多个
    endpoint_role: expert       # expert | yifei | gege | mp-backend
```

| # | 规则 | 判定方式 |
|---|------|---------|
| R8.1 | `name` 全局唯一；重复登记时 hub 启动失败并在日志报错 | hub 启动行为 |
| R8.2 | `scope` 决定可见性：`group` → 仅 `grp_*`；`dm` → 另含 `dm_yifei`。哥哥 token 与亦菲端 token 必须为 `[group, dm]`；专家 token 必须为 `[group]` | 配置逐项检查 + R5.1 实测 |
| R8.3 | `endpoint_role` 取值固定四选一；`from` 为 `gege`/`yifei` 的消息（R4.4/R4.6 人工复位语义）仅允许来自 `endpoint_role` 为 `gege`/`yifei` 的 token | 鉴权逻辑审查 |
| R8.4 | 新增专家流程：哥哥/亦菲拍板 → A-arch 改 `config.yaml` 追加 Agent Card → 重启/热加载 hub → 下发 token。新专家仅凭本文 + token 即可写接入件并联调 | 流程走查 |

## 9. hub 端点约定

base：`http(s)://115.190.64.190:<port>`（端口在 `config.yaml` 配置，默认 `8765`）。

### 9.1 端点表

| 端点 | 协议 | 说明 |
|------|------|------|
| `GET /ws?token=<token>` | WebSocket | 端主连接：订阅、收发、心跳、补发（升级前鉴权，失败返回 401） |
| `POST /messages` | HTTP | 发送消息（body = schema 去掉 `seq`/`ts`；返回入库后完整消息） |
| `GET /messages?conversation_id=&after_seq=&limit=` | HTTP | seq 增量拉取（F4）；`after_seq` 缺省 = 0；`limit` 缺省 100、上限 500 |
| `GET /messages?conversation_id=&from_ts=&to_ts=` | HTTP | 时间段检索（F4），ISO 8601 UTC |
| `GET /conversations` | HTTP | 列出调用者可见会话（按 scope 过滤，R5.2） |
| `GET /healthz` | HTTP | 健康检查：返回 `{"status":"ok","hub_seq":N,"uptime_s":M}`，无需 token |

### 9.2 WS 消息帧（端 → hub）

| 帧 | 格式 | 说明 |
|----|------|------|
| 订阅 | `{"op":"subscribe","conversations":["grp_experts"],"last_seq":12300}` | 连接后首帧必须为它；`last_seq` 触发 R6.4 补发 |
| 发消息 | `{"op":"send","msg":{<schema 去掉 seq/ts>}}` | 等价于 `POST /messages` |
| 心跳 | `{"op":"ping"}` | 见 R6.1 |

hub → 端帧：`deliver`（消息分发/补发，payload 为完整 schema）、`send_ack`（含分配的 `seq`，或 `error` 字段）、`pong`、`catchup_done`、`error`。

### 9.3 错误码表

| HTTP 码 | 代码 | 含义 | 触发条件 |
|---------|------|------|---------|
| 400 | `BAD_SCHEMA` | 消息字段缺失/类型错误 | schema 校验失败 |
| 400 | `BAD_CONVERSATION` | 非法 `conversation_id` | 非 `grp_*` 且非 `dm_yifei` |
| 400 | `BAD_TYPE` | 非法 `type` | 非 text/markdown/system |
| 401 | `AUTH_FAILED` | token 缺失或未知 | 无 token / 未登记 |
| 403 | `FORBIDDEN` | 可见性越权 | 专家 token 访问 `dm_yifei` 等（红线） |
| 409 | `DUP_MSG_ID` | `msg_id` 重复 | 重发已入库消息 |
| 413 | `MSG_TOO_LARGE` | `body` 超 64 KB | 体积超限 |
| 429 | `RATE_LIMITED` | 单端发送超 60 条/分钟 | hub 限流 |
| 500 | `INTERNAL` | hub 内部错误 | — |

警告码（不阻断，出现在响应 `warnings` 数组）：`UNKNOWN_MENTION`（@了未登记 agent）。

## 10. 一致性声明

本文与 `05_项目架构方案.md` 第 3 节关键机制完全一致：seq 全局单序列（不按会话分列）、轮数上限默认 20、会话超时默认 10 分钟、备份信道阈值默认 5 分钟、STOP 强制终止、token 预签发 + hub 侧强制可见性过滤、心跳 + `last_seq` 补发。schema 或机制变更时，必须同步修订本文并显式通知 A-client、A-mp（A-arch 红线）。
